Component A | Backend ingestion

Collect, normalize, and hand off campaign data

Section A runs as a backend job. An operator supplies a campaign configuration and starts the collector; this static page documents its status and data handoff.

Demo data is synthetic; live collection is opt-in. The demo uses real names (Apple iPhone 17 and Coca-Cola Zero Sugar) in synthetic scenarios; its posts are fictional and no API requests are made. Live X reads require approved access and can incur charges. Telegram collection is limited to authorized chats available to the bot.
Input

Campaign job config

The operator provides campaign names, products, search terms, hashtags, account filters, exclusions, and collection limits in a local JSON config.

Ingestion

X first, authorized sources

The backend supports X recent search and authorized account timelines, with Telegram bot updates as a limited secondary source. It uses official APIs only.

Processing

Normalize and preserve evidence

Posts are deduplicated and timestamped. Reply, quote, and repost references, campaign match reasons, source coverage, and run status are kept in Section A sidecars.

Handoff

Shared six-column feed

The export uses the agreed data/posts.csv columns. A reviewed handoff selects one campaign because the shared schema has no campaign ID.

Data flow

campaign config → source adapters → local SQLite + Section A evidence files → reviewed data/posts.csv → Sections B-E

This page does not start a collection run or accept API credentials. The operator runs the Python backend from a trusted computer; credentials remain in an ignored local .env file.
